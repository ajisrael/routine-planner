Refined plan - for review, before implementation

Routine Planner: guided routine setup wizard

At a glance

Why

The app today starts with a blank task library, three full-featured tabs, and no guided path. Building a whole family routine is a single open-ended task instead of a step-by-step flow.

Idea

Wrap creation in a guided setup wizard: who is involved, then one cadence at a time - daily, weekly, monthly - define the tasks, then arrange them on the matching timeline until the whole 30-day routine exists. Afterwards, the current app manages it.

Refined core

The wizard is not a separate data flow. It is a guided view over the same data (same store, same rules, same events), so it is resumable by construction and safe to rerun at any time.

Goal & problem statement

Problem. Starting a routine from scratch means juggling dozens of recurring tasks across three time scales at once, on a blank calendar. Families get overwhelmed before they place a single event.

Goal. A guided, step-by-step creation flow that breaks "build the month" into small, scoped decisions - people, then daily, then weekly, then monthly - each step writing real, persisted routine data. When done, the user owns a full 30-day template and manages it with the existing Tasks / Plan / View flow.

  • 🎯 Guide, do not fork - every action writes the same data the normal app reads.
  • 🔁 Resumable - the wizard derives its state from stored data, so stopping mid-way and coming back later shows exactly where things stand.
  • 👨‍👩‍👧 Any user can build it - the existing real-time sync works unchanged inside the wizard.

Decisions locked in

1

Cadence is a task field

Tasks get a dedicated cadence column (daily / weekly / monthly / custom). Categories stay free-form for grouping and color.

2

Wizard is a view, resumable

Always-reachable "Setup" surface that auto-opens on first run. It reads and writes the same tasks/rules/events, so it resumes from stored data and never duplicates or conflicts with Plan/View.

3

Personas removed

All users can log in by name. Any user can create other users (e.g. Dad, or a child with their own login). Kills is_login_user and the persona concept.

How the wizard fits the app

The Setup surface is a fourth tab next to Tasks / Plan / View. On first run (no tasks in the store) the app lands there. Every stage writes via the same store actions the existing tabs use - so the "wizard" is a guided way of visualizing the same routine data, not a separate pipeline.

The Setup hub: progress from stored data

The hub is the wizard's landing page. It derives each stage's status from the store - no extra flags, no wizard persistence table. Clicking a stage opens it; Back / Next walk the steps in order.

Status derivations (from store data)

  • People - always complete (you are already a member).
  • Daily - count of tasks with cadence=daily; "placed" when a rule + events exist.
  • Weekly - count of cadence=weekly tasks; placed when the rule spans ≥1 weekday.
  • Monthly - count of cadence=monthly; placed when monthly_date is set.

Skip a scale freely - not every family has monthly tasks. Finish is enabled with everything unreachable skipped.

Data model changes

TableChangeWhy
tasks Add cadence TEXT NOT NULL DEFAULT 'custom' CHECK (cadence IN ('daily','weekly','monthly','custom')) First-class grouping for the wizard and the Tasks-tab segmentation. Custom preserves today's free-form recurrence for everything else.
users Rebuild table: drop is_login_user; username TEXT NOT NULL UNIQUE. Backfill NULL usernames from display_name (lowercased, de-duped). Everything can log in; no personas. Assignments (task_assignees) are untouched by the rebuild.
recurrence_rules No change weekly_days / monthly_date already express everything the wizard needs.
scheduled_events No change Materialized occurrences stay the source of truth.

Shared types: Task gains cadence + new exported TaskCadence; User drops isLoginUser, username becomes required. Entities users remain in the same snapshot/realtime collections - the wire protocol shape changes only for those fields.

Arrange-step behavioral contract

The arrange canvases treat placement as pattern editing: a move updates the task's recurrence rule and regenerates its materialized events (same semantics as the existing "change frequency" path - PUT /api/tasks/:id/recurrence with a refStartMinute carries it). After setup, per-day tweaks happen instance-first in the Plan tab.

Daily single-day
  • Canvas: one representative day (Day 1).
  • Place task → rule weekly_days [1-7], ref time = drop.
  • Every subsequent move updates ref time and regenerates all 30 occurrences.
Weekly week grid
  • Canvas: week 1 (Mon-Sun), daily events carried over read-only.
  • Place unplaced task on a day → first drop sets ref time, day added.
  • Drop same task on another day → adds that weekday at the same ref time (drop Y ignored, ghost shows the time).
  • Drag a block to a new time in same column → ref time updates.
  • Drag a block to a different day → that weekday replaces the old one.
  • Drop a block on the rail → removes that weekday; none left → rule "none".
Monthly month grid
  • Canvas: full 30 days with everything placed so far.
  • Tap a monthly task → tap a date cell → that day's hourly view opens with the task armed.
  • Drop at an hour → monthly_date [that day] + ref time.
  • Click a placed block → returns to the day view to reposition.

Tasks tab & task form rework

Tasks tab: cadence segments

  • Lead with a segmented control: All · Daily · Weekly · Monthly · Other.
  • Category filter chips stay as a secondary filter.
  • Cards gain a cadence badge ("Daily", "Weekly", "Monthly", "Custom"); the existing rule and "unscheduled" badges remain.
  • "Other" = cadence custom (interval, one-offs, anything non-template).
  • Deleting a task still cascades to its rule + events.

TaskForm: cadence-first

  • Top segment: Daily / Weekly / Monthly / Custom - it controls the recurrence section that follows.
  • Daily → ref time only. Weekly → Mon-Sun toggles + ref time. Monthly → template day + ref time. Custom → today's full options (one-off, every-N-days).
  • Cadence and rule always agree because the segment drives the rule inputs.
  • The wizard quick-add is this form pre-scoped to the stage cadence.

Risks & documented limitations

Regeneration wipes instance tweaks

Re-arranging a placed pattern in the wizard regenerates rule-linked events (existing v1 behavior, DATA_MODEL 5.3). Mitigation: confirm when a drag would rewrite a task that already has multiple events ("Update every occurrence of X?").

Weekly = one reference time

A weekly task runs at the same time on every selected day (the engine's single reference time). Families that need per-day hours fine-tune individual occurrences in the Plan tab afterwards (instance-first is already supported).

Monthly = one template day

The wizard's monthly step places each monthly task on a single template day (monthly_date). A "1st and 15th" need becomes two tasks, or a second occurrence added manually later.

Persona migration

Existing persona rows become full login users with a backfilled username. Task assignments survive (task_assignees keyed by user id, not by type). Communication is needed so nobody is surprised the kids can now log in.

Two small open choices (annotate to decide)

Setup in the navbar

Recommended: a fourth tab after View (Tasks · Plan · View · Setup). First run lands there automatically.

Alternative: a primary "Set up routine" button that opens the wizard full-screen, leaving three tabs.

First-run hand-off

Recommended: auto-open Setup when the store has no tasks after login; explicit "Skip for now" falls back to the Tasks tab (Setup stays one click away).

Alternative: keep the app landing on Tasks and show a prompt to start the wizard.
